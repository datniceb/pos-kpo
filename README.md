# ПОС — Преподавательская Оценка Студентов

ДЗ-2 по КПО. Консольное приложение: студенты, рубрикатор (критерии), оценки, итог по весам и экспорт итогов в CSV.
Сделано по DDD, архитектура — **Ports and Adapters (Hexagonal)**, паттерны GoF.

## Запуск

Нужен Python 3.10+. Внешних зависимостей у самого приложения нет.

```bash
python main.py        # консольное приложение, данные сохраняются в папку data/
python demo.py        # сквозной сценарий из ТЗ: критерии и студенты -> оценки -> итог -> экспорт
```

Тесты и проверка кодстайла:

```bash
pip install -r requirements-dev.txt
python -m pytest
ruff check .
```

Сквозной сценарий вручную в `main.py`: `1` (студенты) → `3` (критерии) → `6` (оценки) → `10` (итоги) → `11` (экспорт в CSV).

## Архитектура: Ports and Adapters

```
pos/
  domain/            ядро: сущности, VO, инварианты, доменный сервис, порты репозиториев
    errors.py          DomainError — нарушение правил домена
    criterion.py       Criterion (entity)
    rubric.py          Rubric (агрегат) + RubricBuilder
    evaluation.py      Evaluation (value object) + EvaluationFactory
    student.py         Student (entity, корень агрегата с оценками)
    grading.py         стратегии подсчёта итога, декоратор округления, FinalGradeCalculator
    ports.py           StudentRepository, RubricRepository (исходящие порты)
  application/       сценарии (use cases)
    facade.py          PosFacade — все сценарии в одной точке входа
    ports.py           ResultExporter (исходящий порт экспорта)
  infrastructure/    адаптеры
    console.py         ConsoleApp — входящий адаптер (меню)
    json_repositories.py   хранение в JSON + маппинг «словарь из файла ↔ доменный объект»
    memory_repositories.py хранение в памяти (тесты и демо)
    csv_exporter.py    экспорт итогов в CSV
    container.py       DI-контейнер
    composition.py     composition root: какие реализации подставить вместо портов
main.py              точка входа
demo.py              демо-сценарий
tests/               тесты инвариантов, доменного сервиса и сценариев
```

**Стрелка зависимостей — только внутрь:**

```
infrastructure  ──►  application  ──►  domain
```

- `domain` ничего не импортирует из `application` и `infrastructure`: в нём нет консоли, файлов, JSON и CSV.
- `application` знает только домен и порты (абстрактные классы). Про JSON и CSV он не знает.
- `infrastructure` реализует порты (`JsonStudentRepository(StudentRepository)`, `CsvResultExporter(ResultExporter)`) и вызывает фасад.
- Какой адаптер подставить вместо порта, решается в одном месте — `composition.py`. Поэтому JSON заменяется
  на память (в тестах и демо) одной строкой, без правок домена и сценариев.

Порты:
- **входящий** — методы `PosFacade`, их вызывает консоль;
- **исходящие** — `StudentRepository`, `RubricRepository`, `ResultExporter`; их вызывает ядро, а реализуют адаптеры.

## Карта DDD

**Ubiquitous Language** — слова из ТЗ один в один: студент (`Student`), критерий (`Criterion`), рубрикатор (`Rubric`),
оценка (`Evaluation`), итог (`FinalGradeCalculator`).

**Entity vs Value Object.** Вопрос, по которому я различал: «если поменять все поля, это будет тот же объект?»

| Объект | Тип | Почему |
|---|---|---|
| `Student` | Entity | Есть `id`. Поменяли имя — тот же студент. Сравнение только по `id` |
| `Criterion` | Entity | Есть `id`, по нему оценки ссылаются на критерий, критерий можно удалить |
| `Evaluation` | Value Object | `@dataclass(frozen=True)`, сравнение по значению. Исправить оценку = заменить объект новым |

Пример: две оценки «8 баллов за ДЗ, комментарий "ок"» равны (`==` даёт `True`) — это одно и то же значение.
А два студента «Иванов» не равны, у них разные `id`.

**Агрегаты:**
- `Student` — корень агрегата, внутри его оценки (по каждому критерию не больше одной);
- `Rubric` — корень агрегата, внутри критерии курса.

Курс один, поэтому рубрикатор тоже один.

**Инварианты и где они охраняются:**

| Правило | Где проверяется |
|---|---|
| балл в диапазоне `[0, max_score]` критерия | конструктор `Evaluation` (`__post_init__`): оценка принимает сам объект критерия, поэтому 12 из 10 нельзя создать даже в обход фабрики |
| оценка только по критерию из рубрикатора | `EvaluationFactory.create` и ещё раз `Student.put_evaluation` (второй рубеж на случай, если оценку создали в обход фабрики) |
| итог согласован с текущими оценками | итог **нигде не хранится**, `FinalGradeCalculator` каждый раз считает его заново из текущих оценок и рубрикатора |
| `max_score > 0`, вес `> 0`, названия не пустые, нет двух критериев с одинаковым названием | `Criterion`, `Rubric.add_criterion` |
| нет оценок по удалённому критерию | `PosFacade.remove_criterion` удаляет критерий вместе со всеми оценками по нему (консоль переспрашивает) |

**Repository** — порты `StudentRepository` и `RubricRepository` в домене, реализации в `infrastructure`.

**Domain Service** — `FinalGradeCalculator`: итог зависит и от оценок студента, и от весов/максимумов рубрикатора,
поэтому не принадлежит ни студенту, ни рубрикатору. Формулу задаёт стратегия, а сервис следит, чтобы итог был
согласован: рубрикатор не пуст, все оценки студента относятся к текущему рубрикатору, результат в шкале 0..10
(даже если подставить кривую стратегию).

## Решения по предметной области

- Повторное выставление оценки по тому же критерию — это **исправление** (преподавателю не нужно сначала отменять).
- Балл может быть дробным (7.5).
- Тёзки разрешены (у студентов разные `id`), поэтому в списках и в CSV рядом с именем выводится `id`.
- Промежуточный итог студента без единой оценки — 0.
- Итог — по 10-балльной шкале: $\text{итог} = 10 \cdot \frac{\sum_i w_i \cdot s_i / \text{max}_i}{\sum_i w_i}$.
  Веса не обязаны давать в сумме 1, формула нормирует сама.
- Изменение критерия не реализовано (по ТЗ — «по необходимости»): изменить = удалить и добавить заново.
  Так не бывает оценок, которые после уменьшения максимума оказались бы вне диапазона.

## Паттерны GoF

| Группа | Паттерн | Где | Какую боль закрывает |
|---|---|---|---|
| Порождающий | **Factory** | `EvaluationFactory` | единая точка создания оценки: проверяет, что критерий есть в рубрикаторе, и подставляет сам объект критерия из рубрикатора |
| Порождающий | **Builder** | `RubricBuilder` | рубрикатор собирается по шагам, а `build()` выдаёт его только целиком — «всё или ничего». Используется при загрузке из файла: если третий критерий в файле кривой (отрицательный максимум, дубликат названия), не получится полусобранный рубрикатор из двух критериев — программа сообщит о повреждённом файле |
| Структурный | **Facade** | `PosFacade` | консоль не знает про репозитории, фабрику и доменный сервис, только про один класс. Сценарии не размазаны по UI |
| Структурный | **Decorator** | `RoundingDecorator` | округление навешивается поверх **любой** стратегии без изменения её кода. Плюс округление «по-школьному»: встроенный `round(6.5)` в Python даёт 6, а в ведомости должно быть 7 |
| Поведенческий | **Strategy** | `StrictWeightedAverage`, `GradedOnlyWeightedAverage` | разные правила итога: **строгий** (нет оценки = 0, для финальной оценки) и **промежуточный** (только по оценённым критериям, для статистики посреди курса). Без стратегии это был бы растущий `if/elif` внутри доменного сервиса |

Зачем две стратегии: у студента оценено только ДЗ на 10 из 10, а экзамена ещё нет. Промежуточный итог — 10
(по тому, что сдано, он отличник), а строгий — 5 (половина курса не сдана). Обе цифры нужны преподавателю в разное время.

## DI

`Container` (`infrastructure/container.py`) — небольшой DI-контейнер: `register(порт, провайдер)` и `resolve(порт)`,
объекты создаются один раз. Регистрация происходит в `composition.py`. Остальной код зависит от абстракций и сам ничего
не создаёт.

## Тесты

`tests/test_domain.py` — инварианты (балл вне диапазона, включая `nan` и `inf`, критерий не из рубрикатора, обход
фабрики, кривой рубрикатор), исправление оценки, обе стратегии на одних данных, декоратор округления,
согласованность итога с оценками.

`tests/test_application.py` — сценарии через фасад: удаление критерия вместе с оценками, экспорт в CSV,
сохранение между запусками (JSON), повреждённые файлы данных.
